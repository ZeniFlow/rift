## 2. Роли нод

Роль — набор включённых функций в одном бинаре. Всё, кроме control, permissionless.

| Роль | Публичный IP | Что делает | Платно |
|---|---|---|---|
| **Client** | нет | Браузер, VPN, кошелёк. Держит соединения с 1–3 relay. | — |
| **Relay** | интернет-relay да, LAN-relay нет | Рандеву, hole punching, ретрансляция, мосты relay↔relay. Узел DHT. | бесплатно |
| **Host** | нет | Публикует сайт/сервис под доменом (§6). Может сидеть за NAT. | — |
| **Exit** | да | Выпускает VPN-трафик в интернет. Объявляет политику и принимаемые токены. | да |
| **Zone owner** | желательно | Владеет зоной (`.brand`), ставит цены, допускает регистраторов, ведёт лог зоны. Вносит стейк в RIFT. | да |
| **Registrar** | нет | Продаёт домены в зоне по разрешению владельца зоны. | да |
| **Control** | да | Федерация 3 нод (2-из-3). Выпускает/отклоняет/передаёт зоны, takedown, отзывы. Хостит `rift://control.rift` (§6.5). | зоны в RIFT |
| **Witness** | да | Зеркалит логи, подписывает «головы» логов. | — |

**rift-сайты в обычный интернет не выпускаются**: gateway-нод нет. Сайт в `rift://` доступен только из Rift, в этом и смысл.

## 3. Идентичность и адресация

- `NodeID` = публичный Ed25519-ключ ноды (32 байта, в CLI — 64 hex-символа). Хэшировать нечего: ключ и так короткий.
- Оверлейный IPv6 для VPN: `fd72:` + первые 14 байт публичного ключа (сеть `fd72::/16`). Подделать адрес = подобрать Ed25519-ключ под 112 бит.
- Имена `rift://shop.brand` → NodeID через систему имён (trust.md).

## 4. Связность, маршрутизация, маскировка

### 4.1 Порядок соединения A → B
1. Та же LAN (mDNS) → напрямую.
2. Прямой адрес → напрямую.
3. Hole punching через общий relay.
4. Ретрансляция через relay.
5. Многохоп: A → relay₁ → relay₂ → B.

Проверено в e2e (`tests/e2e`): если обе стороны за Linux-MASQUERADE, NAT не пробивается. Ранний входящий пакет пробития занимает порт в conntrack, и NAT отдаёт ответу другой порт (так работают многие домашние роутеры). Тогда трафик идёт через relay. Если хотя бы одна сторона за «лёгким» NAT, путь становится прямым. Чтобы пробивать «жёсткий» NAT с обеих сторон, нужно предсказание портов (как в Tailscale), это на потом.

E2E-шифрование между NodeID всегда. Relay видит NodeID концов и объём, но не содержимое.

### 4.2 Relay в локалке
Любая нода в LAN может быть relay для соседей (телефон с интернетом раздаёт rift ноутбуку без интернета). LAN-relay — обычный relay, найденный через mDNS.

### 4.3 Маршрутизация между relay
Нода публикует в DHT подписанную запись `NodeID → [relay₁, relay₂]`. Публичные relay на старте соединены каждый с каждым (full mesh). → ponytail: full mesh, полноценная маршрутизация при >50 relay.

### 4.4 Транспорты и автоподбор (против ТСПУ)

Противник — DPI уровня ТСПУ: распознаёт протоколы VPN по отпечаткам, режет UDP/QUIC, блокирует IP хостеров, на мобильных сетях бывают белые списки. Один транспорт не выживет, поэтому нужен **набор транспортов + автоподбор**.

Транспорты (все несут один и тот же поток оверлея, relay слушает несколько):

| # | Транспорт | Как выглядит для DPI | Когда спасает |
|---|---|---|---|
| T1 | QUIC (iroh) | HTTP/3 | Нет блокировок — самый быстрый |
| T2 | QUIC с маскировкой SNI/отпечатка под популярный сайт | HTTP/3 к популярному сайту | Режут «странный» QUIC |
| T3 | TCP+TLS по схеме REALITY | Обычный HTTPS к чужому реальному сайту, при чужом ключе отдаёт его | UDP заблокирован, ловят TLS-отпечатки |
| T4 | WebSocket/HTTP2 через CDN | HTTPS к домену за CDN | Заблокированы IP relay |
| T5 | Через отечественный relay | Трафик к российскому хостеру | Режут/тормозят соединения к зарубежным хостерам, белые списки |
| T6 | DNS/другие медленные туннели | DNS-запросы | Последняя надежда (потом, если понадобится) |

**Автоподбор «до победного»:**
1. Клиент определяет «сеть» (идентификатор Wi-Fi или оператор/ASN) и смотрит, какой транспорт сработал тут в прошлый раз → начинает с него.
2. Иначе запускает несколько транспортов параллельно с небольшой задержкой (как Happy Eyeballs). Первый, по которому прошло реальное рукопожатие с relay и проверочный обмен данными, — победитель.
3. «Прошло» — это не «TCP соединился»: ТСПУ любит пропускать начало и рвать/замораживать соединение после первых килобайт. Проверка — передать ≥ 64 КБ туда-обратно.
4. Во время работы — следим за деградацией (обрывы, падение скорости до нуля) → тихо переключаемся на следующий транспорт, не роняя сессии оверлея.
5. Статистика «транспорт × сеть» (анонимно, без IP) может отправляться в сеть → новые клиенты сразу знают, что работает у их оператора. Опционально, позже.

Bootstrap при блокировке IP relay: вшитый подписанный список + мосты (непубличные relay, адреса раздаются по одному через QR/мессенджер) + CDN-фронты (T4).

Реализация (фаза 2, шаг 1, сделано): iroh сам держит несколько путей (прямой UDP, relay) и выбирает рабочий: это и есть базовый автоподбор. Канал до relay — TLS/WebSocket поверх TCP; `--proxy` заворачивает его в любой внешний маскирующий транспорт (REALITY и т.п.), см. [bridge.md](bridge.md). Следующие шаги: встроить REALITY-клиент в riftd (без внешнего бинаря, нужно для мобилок), несколько входов (мост, CDN, RU-relay) с перебором, запоминание рабочего варианта по сети.

### 4.5 Будущее: микроконтроллеры и радио

Цель: ESP-плата как мост между Wi-Fi-сетями, телефоны общаются по Bluetooth без интернета.

- **Relay — тупая труба** и так: ему не нужно расшифровывать трафик. Значит, микроконтроллеру хватит пересылать **кадры** между линками, без QUIC и тяжёлой крипты.
- Что закладываем **сейчас**: формат кадра оверлея не зависит от транспорта (`[dst NodeID][len][зашифрованные байты]`), есть трейт «линк» → потом добавятся BLE, Wi-Fi Direct, serial.
- Железо: **ESP32**, а не ESP8266 (у ESP8266 нет Bluetooth и ~50 КБ RAM). ESP32 умеет Wi-Fi + BLE, Rust на нём живёт (esp-hal / esp-idf).
- Телефоны по BLE: Android — нормально, iOS — фоновый BLE сильно ограничен (работает, пока приложение открыто).
- Оффлайн-режим требует кэша DNS-записей и логов на ноде, чтобы имена резолвились без интернета.

## 5. VPN

Одно ядро (TUN + туннели поверх оверлея), два режима:
- **Mesh** (фаза 1, сделано): свои устройства за NAT видят друг друга по `fd72:…`-адресам. Бесплатно.
  - IP-пакеты едут в QUIC-датаграммах (без задержек из-за потерь); пакет больше датаграммы — отдельным QUIC-стримом. MTU TUN = 1280.
  - Доступ только для нод из списка `--peer` (NodeID или `NodeID@relay`). Чужие соединения закрываются.
  - src каждого входящего пакета обязан совпадать с адресом, выведенным из ключа соединения, dst — с нашим адресом. Иначе пакет отбрасывается.
  - Ноды в одной LAN находят друг друга через mDNS и общаются напрямую.
  - Пока нет: обмена списками peers (каждая сторона прописывает другую сама), IPv4 внутри туннеля, имён вместо адресов.
- **Exit**: трафик в интернет через Exit-ноду, оплата чеками (§7).

ОС: Linux/macOS/Windows — TUN (wintun); Android — `VpnService`; iOS — `NetworkExtension` (лимит ~50 МБ).

## 6. Хостинг

Только онлайн: сайт доступен, пока работает хост. Только внутри Rift.

### 6.1 Любое приложение за HTTP
Как `cloudflared tunnel`: rift проксирует на локальный upstream, стек не важен.

```
rift host shop.brand --upstream http://localhost:3000
rift host api.shop.brand --upstream https://localhost:8443 --upstream-insecure  # self-signed
```

Проходит насквозь: HTTP/1.1 и HTTP/2, стриминг, большие загрузки, **WebSocket и SSE**. Заголовки: `Host` переписывается под upstream, `Forwarded`, плюс **`Rift-Client-Id: <NodeID>`** — проверенный ключ клиента → авторизация без паролей.

TLS внутри rift не нужен: канал зашифрован ключами нод, домен привязан к ключу хоста подписанной DNS-записью.

### 6.2 Статика без своего сервера
```
rift deploy shop.brand ./dist     # собранный React/Vue/что угодно
```
Встроенный файловый сервер в riftd, с SPA-fallback на `index.html`.

### 6.3 rift:// внутри WebView
У кастомной схемы в WebView нет «безопасного контекста» → не работают `crypto.subtle`, Service Worker, часть cookie. Поэтому пользователь видит `rift://shop.brand`, а внутри WebView запросы идут на `https://shop.brand.rift` (зарезервированный псевдо-TLD), который перехватывает ядро. Свой origin у каждого сайта → изоляция cookie.

### 6.4 Адресная строка и обычный интернет
- `rift://x.y` — только Rift.
- `x.y` без схемы — сначала Rift, не нашли — обычный DNS. Rift-домен перекрывает одноимённый обычный: защита от фишинга — ручная проверка заявок на зоны.
- Указан другой протокол (`https://`, `http://`, …) — идём в него: обычный интернет напрямую или через Exit. Исключение — `*.rift`: в обычном DNS его нет, это всегда Rift.

### 6.5 Системная зона `.rift` и сайт control
Зона `.rift` принадлежит control. `rift://control.rift`:
- обозреватель логов: все зоны, домены, регистраторы, overrides, отзывы (читает из логов, ничего не хранит отдельно);
- заявка на зону;
- жалоба на домен/зону (подписана ключом заявителя → не анонимный спам).

Решения принимает control.

Остальные системные адреса: `rift://log.rift` (обозреватель логов), `rift://domains.rift` (поиск и покупка доменов по всем зонам), `rift://wallet.rift`, `rift://docs.rift`.

## 7. Кошелёк и оплата

- Некастодиальный мультитокенный кошелёк на **TON**: ключи только на устройстве. v1: **RIFT** (jetton) + USDT (jetton) + TON.
- **RIFT обязателен** для: оплаты зон у control, стейка владельца зоны (залог, который control может забрать за злоупотребления).
- Остальное (домены, exit) — каждый оператор сам выбирает, какие токены принимает. RIFT — валюта по умолчанию в UI.
- Relay бесплатен.
- **Микроплатежи exit — офф-чейн чеки** через платёжные каналы TON: депозит в контракт → клиент каждые N МБ шлёт подписанный чек на растущую сумму → exit обналичивает последний. Пропавший exit украдёт максимум одну порцию.
- Rust + TON: экосистема слабее, чем у EVM. Проверить в начале фазы 5, какие крейты живые (tonlib-rs и др.); запасной вариант — подписывать сообщения в Rust, а отправлять через HTTP API (toncenter-подобный).

## 8. Ядро и сборка

Rust, AGPL-3.0. Платформы: Linux, macOS, Windows, Android, iOS.

```
librift (Rust, на базе iroh)
 ├─ riftd        CLI/демон: relay, host, deploy, exit, control, witness
 │               (фаза 0: relay = готовый бинарь `iroh-relay`, свой — когда понадобятся транспорты T2–T5)
 ├─ rift-app     Tauri 2: десктоп + Android/iOS
 ├─ VPN-обёртки  wintun / VpnService / NetworkExtension
 └─ (будущее)    rift-mcu: ESP32, пересылка кадров по Wi-Fi/BLE
```

## 9. Инфраструктура старта

3 сервера в разных странах, на каждом: публичный relay + bootstrap, доля control (2-из-3), witness. Root — оффлайн у тебя. См. Q-N6 про сервер в России.
